# d_rocket 2.4.0 Integrations Design

## Intent

Strengthen the integration boundary around the existing d_rocket 2.3.0
runtime and code generators. Payer uses the same model as a form, JSON
contract, enum-bearing REST payload, and realtime/download transport. The
release must make those paths composable and observable without moving
application-specific security decisions into d_rocket.

## Goals

- Keep combined `@Form`, `@Serializable`, enum validation, and `@RestClient`
  scenarios covered by a generated reference fixture.
- Generate serializer registrations for concrete generic response shapes that
  are actually used by generated REST/realtime clients.
- Make transport policies reusable across REST, SSE, and streaming downloads.
- Give retry decisions request context and cancellation, while preserving safe
  defaults for ambiguous mutations.
- Make diagnostic redaction configurable, recursive, and case-insensitive.
- Make HTTP-client ownership explicit in `HttpSseClient`.
- Keep Flutter integration out of the core Dart package.

## Non-goals

- d_rocket will not implement Keycloak, DPoP keys, nonce policy, token renewal,
  or Payer-specific authorization decisions.
- The framework will not automatically retry non-idempotent operations merely
  because a timeout occurred.
- The Flutter adapter will not introduce model controllers or replace
  Flutter's `TextEditingController`; it will bridge an existing form field to
  standard Flutter controls.
- `d_rocket_engine_sqlite` will not change unless a failing integration test
  proves that the new contracts require an engine change.

## Constraints

- Target Dart SDK remains `^3.11.5`.
- The release line is `2.4.0`.
- The public packages remain independently publishable, with lockstep
  constraints where they depend on one another.
- Existing APIs remain source-compatible unless an additive API is impossible.
- One class, enum, or explicit language feature per file.
- Production changes require regression tests written and observed failing
  before the implementation is added.
- Generated files are produced by build_runner and are never hand-edited.

## Approaches considered

### A. One monolithic core change

Implement all seven requests inside `d_rocket` and `d_rocket_builder`, and
place Flutter bindings in the core package. This gives one release surface but
would couple the Dart runtime to Flutter and make transport, diagnostics, and
UI lifecycle changes difficult to review together.

### B. Core runtime plus an independent Flutter adapter (selected)

Implement requests 1, 2, 4, 5, 6, and 7 in the core/generator packages, and
create a separate Flutter package for request 3. The core stays usable by Dart
CLI, server, and mobile code without Flutter; the adapter depends on the
published form APIs and standard Flutter controllers. This preserves the
framework boundary while keeping one coordinated 2.4.0 compatibility line.

### C. Contracts and regressions only

Add fixtures and documentation but defer runtime behavior. This would lower
release risk but would leave the Payer integration gaps unresolved, so it is
not sufficient for 2.4.0.

## Architecture

### 1. End-to-end generated integration fixture

Add a minimal application fixture under tests that combines a form request,
serialization, enum fields, nullable generic response shapes, and a generated
REST client. It will be regenerated with build_runner and exercised through
raw form input, JSON, and a fake HTTP transport. The fixture is the acceptance
contract for codegen composition, not a production API.

### 2. Contract serializer discovery

Extend the builder's registry discovery to inspect generated REST and realtime
method signatures, recursively collect concrete generic shapes such as
`ResponseModel<VehicleResponse>` and
`ResponseModel<List<VehicleResponse>>`, deduplicate them, and emit one
application registration entry. The existing per-class registrations remain
available for compatibility. The registry must not attempt to invent a
serializer for an unconstrained type parameter.

### 3. Optional Flutter adapter

Create a separate package, tentatively `d_rocket_flutter`, containing one
binding widget per control family only where needed, beginning with a text
binding. The binding subscribes to field state, writes user edits through
`bindRaw`, applies programmatic changes back to the controller, exposes
validation errors, preserves selection/composing state where Flutter permits,
and disposes only resources it owns. Compound values remain one model field
contract with an adapter/parser rather than multiple model controllers.

### 4. Shared transport policy

Introduce an additive request/response transport pipeline abstraction in
`d_rocket`. REST, SSE, and download clients can pass the final request through
the same policy stages. The policy receives the final URI and headers, can
produce per-attempt credentials/proofs, and can request a controlled repeat
after a response. Redirect handling must never carry credentials across
origins unless the caller explicitly permits it. Payer supplies its DPoP and
nonce implementation.

### 5. Contextual retry

Add a request context containing method, final URI, payload metadata, attempt,
cancellation state, and transient-failure classification. Preserve the old
`bool Function(Object error)?` callback as a compatibility adapter. The new
decision callback defaults to no automatic retry for ambiguous mutations and
honors cancellation during backoff. Each repeated attempt reuses the logical
request identity/payload but lets the transport policy create fresh proof data.

### 6. Diagnostics policy

Replace the fixed sensitive-header/body lists with an additive
`DiagnosticPolicy`. Header matching is case-insensitive; body redaction walks
maps and nested lists recursively. Defaults include `Authorization`, `DPoP`,
`Cookie`, `Set-Cookie`, `cardNumber`, `cvv`, `access_token`, and
`refresh_token`. Existing opt-out behavior for body capture remains intact.

### 7. Explicit SSE ownership

Add `ownsHttpClient` to `HttpSseClient`, defaulting to the current behavior for
internally created transports and to non-owning behavior for injected shared
transports. `close()` is idempotent, cancels pending requests/subscriptions,
and closes the transport only when ownership is true. Tests cover repeated
close, pending connect, dedicated ownership, and shared transport reuse.

## Package impact

| Package | 2.4.0 responsibility |
| --- | --- |
| `d_rocket` | transport policy, retry context, diagnostics policy, SSE ownership, acceptance fixtures and docs |
| `d_rocket_builder` | generic contract discovery and generated registration |
| `d_rocket_lints` | only if a new diagnostic is justified by the combined fixture; otherwise no behavior change |
| `d_rocket_flutter` | optional Flutter form binding package, separate repository/package |
| `d_rocket_engine_sqlite` | no planned change |

## Acceptance tests

- A form request accepts enum selection and text input through `bindRaw`,
  serializes to JSON, and is sent by generated REST code as typed payload.
- `ResponseModel<VehicleResponse>` and
  `ResponseModel<List<VehicleResponse>>` are registered without manual
  registry edits and deserialize with null and unknown-enum cases covered.
- REST, SSE reconnect, and download paths all invoke the same transport policy
  with the final URI; each retry can receive fresh credentials/proof data.
- A timeout on an ambiguous mutation does not retry by default; an explicitly
  retryable idempotent operation does, and cancellation interrupts backoff.
- Diagnostics redact sensitive headers regardless of header casing and nested
  sensitive body fields without exposing their values.
- `HttpSseClient.close()` is safe twice, releases an owned transport, leaves a
  shared transport usable, and leaves no pending listener after cancellation.
- The optional Flutter adapter covers typing, paste, mid-string editing,
  programmatic uppercase normalization, reset, compound display formatting,
  error propagation, and disposal.

## Release verification

For each changed package: run `dart analyze`, `dart test`, and
`dart pub publish --dry-run`. For the generated fixture also run
`dart run build_runner build --delete-conflicting-outputs`. Publish only after
all packages resolve against the public 2.4.0 dependency constraints and the
generated output compiles without manual edits.
