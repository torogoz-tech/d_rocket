# d_rocket 2.2.0 — model-driven forms

## Goal

Reduce form-capture boilerplate without creating a parallel form model. The
annotated model remains the source of truth for structure, conversion,
validation, object construction, JSON serialization and REST submission.

Forms are part of the `d_rocket` ecosystem. There is no separate
`d_rocket_form` package for this feature.

The API uses the framework's simple names: `Form`, `FormField` and
`FormState`. If an application also imports Flutter symbols with those names,
use an import prefix to resolve the collision. `flutter.Form` is not required.

## Responsibility boundaries

### `d_rocket`

The runtime contains Flutter-agnostic field state, typed conversion,
validation rules, validation results and safe model construction. It does not
depend on SQLite, REST or Flutter widgets, so the same flow works in Flutter,
Dart CLI applications and tests.

### `d_rocket_builder`

The builder generates `*.d_rocket_form.g.dart` only for explicitly annotated
models. Generated code reads the model constructor and annotations, but does
not contain network or SQLite logic.

The generated concerns remain independent:

- `*.d_rocket_serializer.g.dart` for JSON;
- `*.d_rocket_rest_client.g.dart` for REST;
- `*.d_rocket_orm.g.dart` for ORM metadata;
- `*.d_rocket_form.g.dart` for capture and validation.

SQLite, Postgres, web and mobile engines do not participate in form capture.
If the application persists the model, it receives the already-constructed
instance. DevTools can observe validation or submission later, but it is not a
form dependency.

## Physical separation

The implementation follows one responsibility per file. Each public class,
enum and explicit language feature lives in its own file and is exported only
from the appropriate public entry point.

| Concern | Runtime or generator area |
|---|---|
| Field state and errors | `lib/src/form/form_field_state.dart` |
| Form coordination | `lib/src/form/form_state.dart` |
| Nested groups and arrays | `lib/src/form/form_group.dart`, `form_array.dart` |
| Typed input conversion | `lib/src/form/form_value_parser.dart` |
| Validation annotations | `lib/src/form/annotations/` |
| Generated adapter | `d_rocket_builder/src/form/` |

## Annotations

| Annotation | Purpose | Example |
|---|---|---|
| `@Form()` | Opt the model into form generation. | `@Form()` |
| `@FormField(...)` | Describe label, order or a composite binding. | `@FormField(label: 'Email')` |
| `@Required()` | Reject empty or whitespace-only values. | `@Required()` |
| `@Email()` | Validate an email address. | `@Email()` |
| `@Length(...)` | Validate minimum and maximum length. | `@Length(min: 8)` |
| `@Pattern(...)` | Validate a declared regular expression. | `@Pattern(expression: r'...')` |
| `@Uuid(...)` | Validate a canonical UUID and optionally its version. | `@Uuid(version: UuidVersion.v4)` |
| `@Range(...)` | Validate numeric or comparable values. | `@Range(min: 1)` |

`@FormField` is optional. Validation stays on the model; its metadata only
avoids repeating labels, order or control hints in the presentation layer.

## Binding existing controls

The generated form does not impose visual controls. Each field exposes a
generic binding that can be connected to a Flutter control, a web control, a
CLI prompt or a custom component:

```dart
final form = LoginRequestForm();

TextField(
  onChanged: form.email.bind,
  decoration: InputDecoration(errorText: form.email.errorText),
);

TextField(
  onChanged: form.password.bind,
  obscureText: true,
  decoration: InputDecoration(errorText: form.password.errorText),
);
```

For controls that emit raw values, use `bindRaw()`. The generated adapter
configures a `FormValueParser<T>` for numeric, boolean, date and enum inputs.
The control only captures and displays data; it does not decide whether the
value is valid.

## Errors and validation modes

Each error exposes display text, a stable code and the complete error list.
Stable codes support localization and telemetry, for example
`email.required` and `email.invalid`.

Validation can be configured per form. The default mode is `onSubmit`, so a
newly focused field does not show an error while the user is still typing.
The runtime also supports `onChange`, `onBlur` and explicit validation.

Generated forms expose `validate()`, `validateAsync()`, `build()` and
`buildAsync()`. An invalid form never constructs a partially valid model.
Synchronous validation performs no network or persistence operation.

## Login example

The model owns the rules; the generated form owns field state and conversion;
the REST client receives the validated request.

```dart
@Form()
@Serializable()
class LoginRequest {
  const LoginRequest({required this.email, required this.password});

  @FormField(label: 'Email', order: 1)
  @Required(message: 'Email is required')
  @Email(message: 'Enter a valid email')
  final String email;

  @FormField(label: 'Password', order: 2)
  @Required(message: 'Password is required')
  @Length(min: 8, message: 'Use at least eight characters')
  final String password;
}

@RestClient(baseUrl: 'https://api.example.com')
abstract class AuthApi {
  @HttpPost('/login')
  Future<Session> login(@Body() LoginRequest request);
}
```

```dart
final form = LoginRequestForm();

if (form.validate()) {
  final request = form.build();
  final session = await api.login(request);
}
```

The form does not call `jsonEncode` or build an untyped map. Serialization
continues to use the generated `LoginRequest.toJson()` contract.

## REST validation errors

An RFC 7807 response can be applied directly to the generated form:

```dart
try {
  await api.login(form.build());
} on RestHttpException catch (error) {
  form.applyRestError(error);
}
```

Dotted and bracketed server paths are resolved to generated fields. The UI
only reads `errorText`, `errors`, `errorCode` or `hasError` from the field
state.

## Composite bindings

A control can update more than one property without creating a controller per
input. For example, a single `MM/YY` control can bind to two model fields:

```dart
form.bindComposite<String>((String value) => <String, Object?>{
  'expirationMonth': value.substring(0, 2),
  'expirationYear': value.substring(3),
});
```

The same mechanism supports a plate composed of prefix and number, an address
picker that updates several coordinates, or a date-range control.

## Async validation

Remote validators expose a validating state and can debounce calls:

```dart
final form = LoginRequestForm(
  asyncValidators: <AsyncFormValidator<LoginRequest>>[
    (LoginRequest? value) => checkEmailAvailability(value?.email),
  ],
  asyncValidationDebounce: const Duration(milliseconds: 300),
);

final valid = await form.validateAsync();
```

The observable states are `validating`, `valid` and `invalid`. A newer input
value supersedes an older remote validation result.

## Nested forms and dynamic collections

`FormGroup` and `FormArray` compose nested controls without introducing
framework widgets:

```dart
final form = FormGroup();
form.add('email', FormFieldState<String>());
form.add('addresses', FormArray<AddressFormState>());

final valid = await form.validateAsync();
```

Groups propagate enabled/disabled, dirty/pristine and validation state. A
disabled field keeps its value and can be re-enabled without reconstruction.

## Verified contract

The release contract covers:

1. annotations and validation result types in `d_rocket`;
2. independent field and form runtime files;
3. deterministic typed conversion and error messages;
4. generated login fixtures and integration tests;
5. `@Serializable` and `@RestClient` integration;
6. nullable, non-nullable, enum, date and numeric inputs;
7. REST error mapping, asynchronous validation and composite bindings;
8. generated output, analysis, tests and backward compatibility.

Run the generator and tests with:

```bash
dart run build_runner build --delete-conflicting-outputs
dart analyze
dart test
```

Existing models remain compatible when they do not use `@Form`.
