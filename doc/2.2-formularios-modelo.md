# d_rocket 2.2.0 — formularios dirigidos por el modelo

Estado: implementación local en validación final para 2.2.0.

## Objetivo

Reducir el trabajo de captura de formularios sin crear un modelo paralelo. El
modelo anotado seguirá siendo la fuente de verdad para la estructura, la
conversión, la validación, la construcción del objeto, la serialización JSON y
el envío mediante los clientes REST existentes.

La funcionalidad pertenece al ecosistema de `d_rocket`. No se creará un
paquete `d_rocket_form` separado para 2.2.0.

La API usa nombres simples para conservar la nomenclatura del framework. Si
una aplicación también importa los símbolos `Form`, `FormField` o `FormState`
de Flutter, podrá resolver la colisión usando alias de importación. El uso de
`flutter.Form` no es obligatorio para los formularios de d_rocket.

## Situación actual

Estas capacidades ya existen y se reutilizarán:

| Capacidad | Anotación o API actual | Uso en Forms |
| --- | --- | --- |
| Modelo serializable | `@Serializable` | Genera `toJson` y `FromJson`. |
| Clave JSON obligatoria | `@JsonKey(requiredKey: true)` | Rechaza claves ausentes al deserializar. |
| Normalización | `@Format(...)` | Se reutiliza para trim, mayúsculas, fechas y formatos personalizados. |
| Cliente HTTP | `@RestClient` | Declara el cliente que recibirá el modelo. |
| Endpoint POST | `@HttpPost` | Envía el modelo mediante `@Body`. |
| Parámetro de cuerpo | `@Body` | Convierte el modelo serializable en el cuerpo de la petición. |

`d_rocket` ya ofrece validación de negocio genérica mediante las anotaciones de
Forms y `d_rocket_builder` genera los adaptadores correspondientes. `required`
en el constructor y `requiredKey: true` no sustituyen reglas como correo
electrónico, longitud o rangos; esas piezas son nuevas en 2.2.0.

## Diseño separado por responsabilidad

### `d_rocket`

Contiene el runtime agnóstico de Flutter para el estado de cada campo, la
conversión tipada, las reglas de validación, el resultado de validación y la
construcción segura del modelo. No depende de SQLite, REST ni de widgets de
Flutter, para que el mismo flujo funcione en Flutter, Dart CLI y pruebas.

### `d_rocket_builder`

Genera, únicamente para modelos optados explícitamente, un archivo
`*.d_rocket_form.g.dart`. El código generado conocerá el constructor y las
anotaciones del modelo, pero no tendrá lógica de red ni acceso a SQLite.

Los outputs permanecen separados:

- `*.d_rocket_serializer.g.dart` para JSON;
- `*.d_rocket_rest_client.g.dart` para REST;
- `*.d_rocket_orm.g.dart` para ORM;
- `*.d_rocket_form.g.dart` para captura y validación.

Los engines SQLite, Postgres, web y mobile no participarán en la captura. Si
la aplicación persiste el modelo, recibirá la instancia ya construida. DevTools
puede observar validaciones o envíos en una fase posterior, pero no es una
dependencia del formulario.

## Separación física

La implementación respeta la regla de una responsabilidad por archivo y se
distribuye así:

```text
d_rocket/lib/src/form/
├── annotations/form.dart
├── annotations/form_field.dart
├── annotations/email.dart
├── annotations/length.dart
├── annotations/pattern.dart

├── annotations/required.dart
├── form_input.dart
├── form_error.dart

├── form_value_parser.dart
```

Los nombres definen la organización pública de la implementación 2.2.0.
Cada clase, enum o funcionalidad explícita deberá permanecer en su propio
archivo; los exports públicos se agregarán únicamente después de que existan
las implementaciones y sus pruebas.

## Anotaciones nuevas de 2.2.0

Se agregaron a `d_rocket`, en archivos independientes, y son consumidas por
`d_rocket_builder`:

| Anotación | Propósito | Ejemplo |
| --- | --- | --- |
| `@Form()` | Optar por generar el adaptador. | `@Form()` |
| `@Required()` | Rechazar vacío o solo espacios. | `@Required(message: '...')` |
| `@Email()` | Validar el formato de correo. | `@Email()` |
| `@Length(min: ..., max: ...)` | Validar longitud de texto. | `@Length(min: 8)` |
| `@Pattern(...)` | Validar una expresión regular declarada. | `@Pattern(r'...')` |
| `@Uuid(...)` | Validar un UUID canónico y, opcionalmente, su versión. | `@Uuid(version: UuidVersion.v4)` |
| `@Range(min: ..., max: ...)` | Validar valores numéricos o comparables. | `@Range(min: 1)` |
| `@FormField(...)` | Metadatos de captura, no reglas de negocio. | `@FormField(label: 'Correo')` |
| `FormInput` | Tipo de control sugerido por el modelo. | `FormInput.password` |

`@FormField` es opcional. La validación vive en el modelo; sus
metadatos solo evitarán repetir etiquetas, orden o tipo de control en la
pantalla. No se agrega una interfaz obligatoria: el builder genera clases
concretas.

## Trazabilidad

| Necesidad | Fuente | Generador | Resultado verificable |
| --- | --- | --- | --- |
| Capturar texto | Campo final del modelo | Form builder | Campo con valor bruto y conversión. |
| Normalizar entrada | `@Format` | Form builder/runtime | El modelo recibe el valor normalizado. |
| Validar requerido | `@Required` | Form builder/runtime | Error asociado al campo. |
| Validar email | `@Email` | Form builder/runtime | Correo inválido no construye el modelo. |
| Validar contraseña | `@Length` | Form builder/runtime | Longitud mínima aplicada antes del envío. |
| Crear request | Constructor del modelo | Form builder | Instancia válida de `LoginRequest`. |
| Convertir a JSON | `@Serializable` | Serializer builder | `request.toJson()`. |
| Enviar por REST | `@RestClient`, `@HttpPost`, `@Body` | REST builder | POST con el JSON generado. |
| Persistir después del envío | `@Table`, `@Column` | ORM builder + engine | Persistencia separada y opcional. |

## Binding y mensajes de error

El formulario no impondrá controles visuales propios. Cada campo generado
expondrá un binding genérico para que la aplicación lo conecte a cualquier
control que ya utilice:

```dart
TextFormField(
  initialValue: form.email.value,
  onChanged: form.email.bind(),
  decoration: InputDecoration(
    labelText: 'Correo electrónico',
    errorText: form.email.error,
  ),
)
```

El mismo contrato debe funcionar con `Checkbox`, `Switch`, dropdowns,
selectores de fecha y controles de terceros. El campo generado expondrá:

```dart
form.email.value;
form.email.error;
form.email.errors;
form.email.errorCode;
form.email.hasError;
form.email.isTouched;
form.email.bind();
form.age.bindRaw(); // para controles que emiten un valor crudo
```

Las reglas y sus mensajes predeterminados vivirán en el modelo:

```dart
@Required(message: 'El correo es obligatorio')
@Email(message: 'Ingresa un correo válido')
final String email;
```

Además del texto, cada error tendrá un código estable para localización o
telemetría, por ejemplo `email.required` y `email.invalid`. El control solo
presentará `field.error`; no decidirá si el valor es válido.

Cuando el tipo emitido por el control no coincide con el tipo del modelo, el
adaptador generado configura un `FormValueParser<T>` para los inputs
`number`, `boolean` y `date`. El control puede usar `bindRaw()` y el modelo
recibe el valor convertido o un error `conversion.invalid`.

La validación podrá configurarse por formulario:

```dart
final form = LoginRequestForm(
  validationMode: FormValidationMode.onSubmit,
);
```

Los modos disponibles son `onChange`, `onBlur`, `onSubmit` y `manual`. El modo
predeterminado es `onSubmit` para no mostrar errores mientras el usuario aún
está escribiendo.

## Ejemplo: formulario de login

Este es el API implementado en 2.2.0. Las anotaciones `@Form`, `@Required`,
`@Email`, `@Length` y `@FormField` son consumidas por el builder de formularios;
las demás pertenecen al API actual de d_rocket.

`FormInput` es un enum independiente. No convierte el modelo en un widget
ni agregará una dependencia de Flutter al paquete core.

### `login_request.dart`

```dart
import 'package:d_rocket/d_rocket.dart';

part 'login_request.d_rocket_serializer.g.dart';
part 'login_request.d_rocket_form.g.dart';

@Serializable()
@Form()
class LoginRequest {
  LoginRequest({
    required this.email,
    required this.password,
  });

  @FormField(label: 'Correo electrónico', order: 1)
  @Required(message: 'El correo es obligatorio')
  @Email(message: 'Escribe un correo válido')
  @JsonKey(requiredKey: true)
  final String email;

  @FormField(
    label: 'Contraseña',
    order: 2,
    input: FormInput.password,
  )
  @Required(message: 'La contraseña es obligatoria')
  @Length(min: 8, message: 'Debe tener al menos 8 caracteres')
  @JsonKey(requiredKey: true)
  final String password;
}

```

### `auth_api.dart`

```dart
import 'package:d_rocket/d_rocket.dart';

import 'login_request.dart';

@RestClient(baseUrl: 'https://api.example.com')
abstract class AuthApi {
  @HttpPost('/auth/login')
  Future<SessionResponse> login(@Body LoginRequest request);
}
```

El archivo generado `login_request.d_rocket_form.g.dart` contiene el adaptador
concreto `LoginRequestForm`; el archivo generado del cliente REST sigue siendo
independiente. Estos nombres y métodos forman el contrato de 2.2.0.

Consumo esperado desde Flutter:

```dart
final form = LoginRequestForm();

form.email.bind()(emailController.text);
form.password.bind()(passwordController.text);

if (!form.validate()) {
  setState(() {});
  return;
}

final request = form.build();
final session = await authApi.login(request);
```

El flujo implementado es:

```text
TextEditingController → LoginRequestForm → validate()
        → LoginRequest → toJson() → @Body + @HttpPost → respuesta REST
```

El formulario no llama directamente a `jsonEncode`, no construye mapas
manualmente, no accede a SQLite ni duplica `LoginRequest`.

## Criterios verificados en 2.2.0

1. Un modelo con `@Form` genera un archivo independiente y compila con Dart
   3.11.5.
2. Un modelo sin `@Form` conserva exactamente el comportamiento actual.
3. `String`, `String?`, `int`, `double`, `bool`, `DateTime` y enums tienen
   conversión y validación cubiertas por pruebas.
4. Un valor vacío, inválido o no convertible produce un error de campo y nunca
   una instancia parcialmente válida.
5. Cualquier control puede conectarse mediante `field.bind()` sin requerir un
   widget propio de d_rocket.
6. Los errores exponen texto, código estable, lista de errores y estado del
   campo.
7. Los modos `onChange`, `onBlur`, `onSubmit` y `manual` tienen pruebas.
8. `validate()` no realiza red ni persistencia.
9. El request construido usa el serializer y el cliente REST existentes.
10. Se agregan pruebas del runtime, del builder, de JSON/REST y de
   no-regresión.
11. `dart analyze`, `dart test` y `dart run build_runner build
   --delete-conflicting-outputs` pasan en los repositorios afectados.

## Mapa de componentes implementados

1. Anotaciones y tipos de resultado de validación en `d_rocket`.
2. Runtime de campo y formulario en archivos independientes.
3. `FormBuilder` y output separado en `d_rocket_builder`.
4. Conversión tipada y mensajes de error deterministas.
5. Fixtures de login y pruebas de generación.
6. Integración con `@Serializable` y `@RestClient`.
7. API final y changelog de 2.2.0.

## Objetivos de desarrollo

### Objetivo 1 — Contrato de anotaciones del modelo

**Responsable:** `d_rocket`.

Definir y probar `@Form`, `@Required`, `@Email`, `@Length`, `@Pattern`,
`@Range`, `@FormField` y `FormInput`. Cada clase o enum vivirá en su archivo
independiente y se exportará únicamente desde el punto público correspondiente.

**Cierre:** las anotaciones compilan, validan sus argumentos y tienen pruebas
unitarias. Un modelo sin estas anotaciones conserva el comportamiento actual.

### Objetivo 2 — Runtime de campo y errores

**Responsable:** `d_rocket`.

Implementar el estado tipado de cada campo y sus errores: `value`, `error`,
`errors`, `errorCode`, `hasError`, `isTouched` y `bind()`.

**Cierre:** un campo puede recibir valores sin depender de Flutter, ejecutar sus
reglas y devolver errores deterministas con texto y código estable.

### Objetivo 3 — Formulario y modos de validación

**Responsable:** `d_rocket`.

Implementar la coordinación del formulario, `validate()`, `build()` y los
modos `onChange`, `onBlur`, `onSubmit` y `manual`.

**Cierre:** un formulario inválido nunca construye un modelo parcialmente
válido; `validate()` no realiza red ni persistencia.

### Objetivo 4 — Conversión tipada

**Responsable:** `d_rocket` y pruebas compartidas.

Cubrir `String`, `String?`, `int`, `double`, `bool`, `DateTime`, enums y valores
nulos. La conversión debe respetar `@Format` y los conversores existentes.

**Cierre:** cada tipo tiene pruebas de entrada válida, entrada inválida,
entrada vacía y entrada nula cuando corresponda.

### Objetivo 5 — Generación del formulario

**Responsable:** `d_rocket_builder`.

Agregar un builder opt-in que genere `*.d_rocket_form.g.dart`, sin modificar ni
mezclar las salidas del serializer, REST, ORM o realtime.

**Cierre:** el builder genera campos y constructor correctos, detecta errores
de configuración con mensajes claros y no genera archivos para modelos sin
`@Form`.

### Objetivo 6 — Binding con controles existentes

**Responsable:** contrato público de `d_rocket` y documentación Flutter.

Verificar que `field.bind()` pueda conectarse a `TextField`,
`TextFormField`, `Checkbox`, `Switch`, dropdowns, selectores de fecha y
controles externos, sin imponer widgets propios.

**Cierre:** existen ejemplos y pruebas de integración que demuestran que los
controles solo capturan y presentan datos; la validación permanece en el
modelo.

### Objetivo 7 — Integración JSON y REST

**Responsable:** `d_rocket_builder`.

Conectar el modelo construido con `@Serializable`, `toJson()` y los clientes
generados por `@RestClient`, `@HttpPost` y `@Body`.

**Cierre:** el formulario de login produce un `LoginRequest` válido y el
cliente REST recibe ese modelo sin mapas ni JSON escritos manualmente.

### Objetivo 8 — Regresión, documentación y release

**Responsable:** ambos repositorios.

Agregar fixtures de login, pruebas de no-regresión, documentación final y
changelog de 2.2.0. Ejecutar generación, análisis y pruebas en los repositorios
afectados.

**Cierre:** pasan `dart analyze`, `dart test` y
`dart run build_runner build --delete-conflicting-outputs`; se verifica además
que los modelos existentes de 2.1.0 continúan compilando sin `@Form`.

## Extensiones de 2.6.0

`FormFieldState` permite deshabilitar un campo sin perder su valor, cancelar
validaciones asíncronas pendientes y excluirlo de la validación. `FormGroup` y
`FormArray` propagan ese estado a sus controles anidados. `FormValidators`
incluye reglas reutilizables para `requiredTrue`, igualdad, pertenencia,
rangos, comparación, contención y validación Luhn de tarjetas.

`@FormField` también puede describir un control compuesto sin acoplarlo a
Flutter:

```dart
@FormField(
  binding: FormBinding(fields: <String>['expiryMonth', 'expiryYear']),
)
final String expiry;
```

El builder conserva esos destinos en `FormFieldDefinition.binding` y rechaza
destinos inexistentes, duplicados o autorreferenciados durante la generación.
El control de la aplicación solo debe enviar un mapa con los nombres
declarados; la capa de presentación sigue siendo independiente del framework.

Los errores RFC 7807 pueden llegar con rutas como `email`, `user.email` o
`user["email"]`; `FormState.applyProblemDetails` y `applyRestError` resuelven
esas rutas sin que la pantalla tenga que traducirlas manualmente.
